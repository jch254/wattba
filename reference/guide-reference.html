A practical guide for non-engineers

Getting going with AI

From "I chat with Claude sometimes" to "Claude builds small things on my computer while I check its work".

For NZB

There is one trick that runs through this whole guide: you get one AI to write the instructions, then hand those instructions to another AI that does the work. Once you have seen it, you will use it for everything. This guide points that trick at your own computer. You will not need to learn to code. You will need to read what the agent plans, say yes or no and keep your work in one folder. Go slow, keep it small and when you get stuck, send me a thread link and I will jump in.

A lot of the thinking in here comes from Matt Shumer, who writes a newsletter called Something Big Is Happening. He has spent years building AI companies and he writes about this stuff in plain English better than anyone I know. I link his articles where they fit. Read them.

Why now

Building with AI now feels like describing what you want in plain English and watching it appear. Engineers have had that experience for the last year or so. Everyone else is about to have it too, and right now there is a short window where most people are still ignoring it. The other thing that changed is price. A result that cost a lab hundreds of thousands of dollars in late 2024 now comes out of a twenty dollar a month subscription. In AI, "this year's million-dollar breakthrough is next year's $20 subscription." So the thing you could not afford to build last year is probably a weekend project now.

01

How to think about AI tools

A chatbot answers. An agent works. That is the whole idea in six words.

When you type into Claude and it replies, that is a chat. You ask, it answers. Then it is up to you to go and do something with the answer. Ask it for a recipe and you get a recipe. Ask it for an email and you get an email. Claude gives you words, and the doing is still yours.

An agent is Claude with hands. You point it at a folder on your computer and it can read the files in there, edit them, run commands (the typed instructions a computer understands) and then check whether the result worked. If something fails, it reads the error and tries again. You are still in charge, because it shows you what it plans to do and you approve or reject each change.

The loop: you write a prompt, the agent works on your files, you review what it did. Accept it or send it back with a comment. Repeat.

The review step is the whole job

Engineers spend most of their time reading, not typing. With an agent, that is now your job too. You do not need to understand every line. You need to check that what it says it did matches what you asked for.

The closest thing I can compare it to is briefing a contractor. You are not typing into a chat box, you are handing someone a job. A contractor you have briefed badly does not stop and ring you. They guess, and they build the guess. Agents are the same. If your brief leaves a question open, the agent will not ask it. It will pick an answer and keep going. That is why the next section is about the brief.

02

Meta prompting

Ask Claude to write the prompt first. This is the trick from the front page, and it is the fastest way to a good result.

Here is the move. Instead of typing your request straight into the agent, you open a normal Claude chat and ask it to write a good prompt for you. Then you paste that prompt into the agent. It works because Claude is better at being specific than you are when you are in a hurry. It remembers to ask about the things you would have forgotten. Meta prompting is the name for it: using one AI to write the instructions for another. The second AI here is an agent that will change files on your computer, so the prompt matters more than it would in a chat.

Matt Shumer's three Cs

This is the framework I use. It boils an agent brief down to context, constraints and composition. Context is everything the agent needs to know and every file it will touch. The test for whether you have given enough: could a new hire do this without coming back to ask you anything? Think of it as the intern test. Constraints are the rules, and the most useful one is a phrase: "don't finish until". Tell the agent what to check before it is allowed to say it is done. Composition is the shape of the result you want, because the format changes how it thinks.

The other rule that goes with it: give it the goal, not the steps. Say where you want to end up and what must always be true along the way (I think of those as house rules), then let the agent work out the route. One line from his piece that I keep coming back to: "Every step I dictate is just me overriding its judgment with mine, and mine is usually worse."

Read: Prompting AI agents and How I prompt Fable.

The anatomy of a solid prompt

Goal

One sentence on what you want to exist at the end.

Context

Who it is for, what already exists, why you want it.

Constraints

Limits. Keep it simple, no sign-ups, must work on a phone, do not touch these files.

What done looks like

How you will know it worked. "I open index.html and see my name and three photos." Vague words like "high quality" let the agent stop at its own idea of good enough, which is usually lower than yours.

Output format

Do you want a plan first? A single file? A list of changes?

An example

A link or a short description of something close to what you want.

Before and after

Make me a website
After
Goal: a one page personal site for NZB, a maker and photographer.

Context: I have no code yet. I have four photos in the photos folder and a short bio in bio.txt.

Constraints: plain HTML and CSS only, no frameworks, no sign ups, must look good on a phone, dark background.

Done looks like: I open index.html in a browser and see my name, the bio and the four photos in a grid, with an email link at the bottom.

Output: show me a short plan first and wait for my ok before writing files.

The prompt writer

Paste this into a normal Claude chat whenever you have a task. It interviews you, then hands you a structured prompt you can drop into an agent.

Copy this into Claude
I want you to write a prompt for an AI coding agent that works on files on my computer. I am not a programmer.

First, ask me questions one at a time, no more than five, until you understand: what I want to exist at the end, who it is for, what I already have, any limits (time, tools, things to avoid) and how I will know it is finished.

Then write one structured prompt with these headings: Goal, Context, Constraints, What done looks like, Output format, Example. Under Constraints include a line starting "Don't finish until" that tells the agent what to check before it says it is done. Keep it under 250 words, use plain language and end it with "Show me a short plan first and wait for my ok before changing any files."

Do not start writing the prompt until you have asked your questions.
Tip

Save the prompt writer somewhere handy (a note on your phone is fine). You will use it more than anything else in this guide.

03

Claude Code basics

Claude Code is the agent. It runs in a project folder and does the work.

Claude Code is a program from Anthropic that runs Claude as an agent on your computer. You open it inside a folder, type what you want and it reads, writes and runs things in that folder. It is text based, which looks intimidating for about ten minutes and then feels like chatting.

It needs a paid Claude plan (at the time of writing, Pro or Max) or a pay as you go developer account. Plans and prices change, so check docs.claude.com before you buy anything.

Install and open it

1
Open the terminal

The terminal is a window where you type commands. On a Mac it is called Terminal (search for it with Spotlight). On Windows use PowerShell.

2
Run the install command from the docs

The Claude Code page on docs.claude.com has a one line install command for Mac, Windows and Linux. Copy it from there rather than from here, because it changes.

3
Make a project folder

Create a folder for this project only, for example my-site in your Documents. Everything Claude Code does stays inside it.

4
Go into that folder

In the terminal type cd, a space, then drag the folder into the window and press Enter. That moves the terminal into the folder.

5
Start Claude Code

Type claude and press Enter. The first time it will ask you to sign in with your Claude account.

Terminal
cd ~/Documents/my-site
claude

Four habits that make it go well

Ask for a plan before changes

End your request with "show me a plan first and wait for my ok". Claude Code will list what it intends to do. Read it. If a step looks wrong, say so before anything happens. The docs also describe a plan mode you can switch on so it never edits without asking.

Approve or reject each edit

When it wants to change a file or run a command, it asks. Yes lets it through and no stops it. You can type why. You are never obliged to accept.

Give the project standing instructions in CLAUDE.md

CLAUDE.md is a plain text file in your project folder that Claude Code reads every time it starts. Put in the things you would otherwise repeat: what the project is, what to avoid, how you like things written. Typing /init inside Claude Code creates a starter one for you.

Use skills for repeatable jobs

A skill is a reusable pack of instructions you can call by name. I keep one that holds my writing style rules, so every document Claude writes for me sounds like me instead of like a robot. You could make one for "how I like my photos laid out". The docs explain where skill files live. One warning: skills written for older models tend to over explain and over constrain, which can make a newer model worse. Keep yours short and revisit them when the model changes.

Example CLAUDE.md
# About this project

This is NZB's personal website. One page, plain HTML and CSS, no frameworks.

# Rules

- Always show me a plan and wait for my ok before changing files.
- Keep explanations short and in plain English. I am not a programmer.
- Do not add anything I did not ask for.
- Never touch the photos folder.
If it offers to skip permissions, say no

There are settings that let Claude Code run without asking. Leave them off. The asking is the safety net.

04

Delta as home base

Delta is where you should spend most of your time. Claude Code does the work, Delta is where you watch, review and share it.

Delta (delta.dev) comes from the team behind the Zed editor. It is built for exactly the loop from section one: you ask, an agent works, you review. Each task lives in a thread, which keeps the conversation with the agent and the code changes it made together in one place, so you can scroll back and see why something changed.

Experiments cannot wreck the original

Delta works in a separate copy of the project for each thread. If a thread goes sideways you close it and the original is untouched.

Comment on the exact spot

You can leave a comment on a specific line of code or a specific message in the conversation to ask for a change. "Make this heading bigger" pointed at the heading beats describing it.

Share a thread link with me

Every thread has a link. Send it to me and I can open it, read what happened and help, without you having to explain anything over the phone.

Claude Code stays the engine

Your Claude Code sessions can sync into Delta threads. Nothing about how the agent works changes. Delta gives it a home with history, comments and sharing.

Delta is new

It is in public beta, so things will keep changing. If the sign up flow on delta.dev looks different from what I describe, follow delta.dev/docs. If anything in Delta is not working for you yet, everything in this guide still works with Claude Code and Zed on their own.

Your first thread

1
Open your project

Start Delta and open the same project folder you used with Claude Code. If Delta asks to connect Claude Code, say yes.

2
Start a thread and ask for one small change

Something you can check in ten seconds. "Change the heading to my full name" is perfect. Ask for a plan first.

3
Read the plan, then read the change

Delta shows the conversation and the files that changed side by side. Look at the before and after. Does it match what you asked for?

4
Comment where it is wrong

Click the line or the message, leave a comment saying what you want instead and let the agent have another go.

5
Accept it

When you are happy, accept the change so it lands in the real project. Then start a new thread for the next thing.

A good first request
In index.html, change the heading text to my full name and make the background colour a touch warmer. Show me a plan first and wait for my ok.
05

Zed for the full editor experience

Zed is a fast code editor. Use it when you want to see every file and poke at things yourself.

An editor is a program for opening and changing text files, which is what code is. Zed (zed.dev) is a quick, clean one. Open your project folder in it and you get a file list down the side and the contents in the middle. You can also run Claude as an agent inside Zed, which is handy for small hands on tweaks.

Add Claude Agent to Zed

1
Install Zed and open your folder

Download it from zed.dev, open it and choose your project folder.

2
Open the Agent Panel

It is the panel for talking to agents inside Zed. There is a button for it in the corner of the window, or open it from the View menu.

3
Add an agent from the ACP Registry

In the Agent Panel look for Add Agent, then Install from Registry and pick Claude Agent. ACP is the Agent Client Protocol, a shared language that lets editors like Zed talk to agents like Claude. The registry is the list of agents that speak it.

4
Sign in with /login

Start a new thread with Claude Agent, type /login and follow the prompts to sign in with your Claude account. The exact steps are on zed.dev/docs under External Agents.

Delta or Zed?

Delta
  • Planning a task
  • Reviewing what the agent did
  • Sharing a thread with me
  • Getting help when stuck
Zed
  • Browsing the files yourself
  • Small hands on tweaks (text, a colour)
  • Seeing the whole project at once
  • Opening a file the agent mentioned

One engine, one folder, two windows onto it. Delta for the conversation and the review, Zed for the files.

06

First project: build yourself a website

Everything above, used once, end to end. Budget an hour.

1
Set up the folder

Make a folder called my-site. Inside it, make a photos folder with a few images and a bio.txt file with a paragraph about you.

2
Write the prompt with the prompt writer

Open a normal Claude chat, paste the prompt writer from section two and answer its questions. You will end up with something like the prompt below. Copy it.

3
Start a Delta thread

Open my-site in Delta, start a thread and paste the prompt. Read the plan it comes back with. If the plan mentions anything you did not ask for, say so. Then give it the ok.

4
Review the build

It should create index.html and style.css. Open index.html in your browser (double click it). Does it show your name, your bio and your photos? Comment in the thread on anything that is off and let it fix it. Accept when it is right.

5
Tweak it yourself in Zed

Open the folder in Zed, click index.html and change a word in the bio. Save, refresh the browser. Then open style.css, find a line with a colour like #0a0f0b and change it. Save, refresh. That is you editing code.

The prompt you will end up with
Goal: a one page personal website for NZB.

Context: I am not a programmer. This folder is empty apart from a photos folder with my images and a bio.txt with a short paragraph about me.

Constraints: one index.html file and one style.css file, no frameworks, no sign ups, no tracking. Dark background, big photos, easy to read on a phone. Do not change anything in the photos folder. Don't finish until you have checked that every photo in the photos folder shows on the page and the page has no broken links.

What done looks like: I open index.html in my browser and see my name, the bio from bio.txt, all the photos in a grid and an email link at the bottom.

Output format: show me a short plan first and wait for my ok before writing files. When finished, tell me how to open the page.

Example: the feel of a simple photographer portfolio page, mostly images, very little text.
Where to go next

Once the page exists, every new idea is a new thread. "Add a contact form", "make the photos open bigger when tapped", "add a page for my woodworking". Same loop each time: prompt writer, thread, plan, review, accept.

It only exists on your machine for now

At this point the site is a folder on your computer. Nobody else can visit it. Getting it live on the internet needs hosting sorted, and that is a separate job with its own choices. I am leaving it out of this guide on purpose. When you have something you want people to see, tell me and we will sort it then.

07

Staying safe

Four rules. They cover almost everything that goes wrong.

1
Never paste secrets into a prompt

No passwords, no API keys (long codes that let a program use a paid service), no bank details, no one else's private information. If a tool needs a key, the docs will show a proper place to put it. A prompt is never that place.

2
Read the plan before you approve

Every time. If a plan includes deleting things, installing things or touching files outside your project, stop and ask why.

3
Keep work in a project folder

Open agents in my-site, never in your home folder or your whole Documents. What the agent can see is what the agent can change.

4
Make mistakes undoable

Delta's separate copies mean a bad thread can be thrown away. Outside Delta, ask Claude Code to "set up Git and commit" before big changes. Git is a save history for a folder, and a commit is one saved snapshot you can go back to.

If something feels off, stop

Reject the change, close the thread and message me. Nothing in a project folder is urgent enough to guess.

Why the asking matters

An agent that is trying hard to finish will sometimes find a route you did not intend. It is not being sneaky. It has a goal, it hits a wall and it looks for a way around, and the way around might be something you would never have agreed to. The models you will use have a lot of guard rails, but this is the reason you keep the approval prompts on and keep the agent inside one folder. Every yes you give is a small decision that stays yours.

My practical advice, which lines up with what people who run agents on their own work every day have found: start with tasks you already know well, so you can tell whether it did them right. Start with the strictest approval settings and loosen them only after the agent has earned it.

08

Where this is heading

Two things worth knowing about before you get too settled.

A new kind of model that does not chat

There is a new kind of AI that does not chat at all. It makes decisions. It is called Jev. You hand it a situation and a list of possible decisions, it picks one and tells you how sure it is. Because it is not writing paragraphs, it is dramatically faster and cheaper than the models you have used so far.

I have been testing it for work and it is legit. To get a feel for what people are doing with it, have a look at this gallery of projects built with Jev. One builder used it to make an agent that finds flights in about seven seconds for less than half a cent. Another taught a car to drive itself in a driving game and it went a full minute on the highway without a crash.

Why it matters: a lot of work is small decisions made over and over. Is this message urgent? Is this photo worth keeping? Asking a top model every one of those questions has been too slow or too expensive. A job that costs a hundred dollars on a top model costs well under a dollar on Jev. At that price a lot more is worth automating. Once you have a site running, ask yourself what you sort by hand all day, and test it there.

I also put out my first YouTube video about Jev, here. I did it on a whim so the quality is low, but it goes deeper than this page does.

If it goes well

After all the warnings, it is worth reading something hopeful. The price of using AI at the original ChatGPT's level fell by more than 280 times between late 2022 and late 2024. If that keeps going, things like personalised medicine and a world class tutor for every kid end up within reach of ordinary people, not only companies. Matt Shumer puts the stakes better than I can: "I think a world where someone you love finds a lump, and you still sleep that night, is really on the table." The small version of that for you is this: the tools in this guide are the same ones the professionals use, at the same price. There is no upgraded version being kept from you.

Glossary

agent

An AI that can act, not only answer. Reads and edits files, runs commands, checks its own work.

prompt

What you type to an AI. The better it is structured, the better the result.

repository

A project folder with a Git save history attached. Often shortened to repo.

terminal

A window where you type commands to the computer instead of clicking. Claude Code runs in one.

commit

One saved snapshot of a project in Git. You can go back to any commit.

Git

The tool that keeps that save history. Ask the agent to set it up; you rarely need to touch it directly.

thread

In Delta, one task: the conversation with the agent plus the changes it made, kept together.

editor

A program for opening and changing text files, which is what code is. Zed is one.

ACP

Agent Client Protocol. A shared language that lets editors talk to agents. Why Zed can run Claude.

CLAUDE.md

A text file in your project that Claude Code reads on every start. Your standing instructions.

skill

A reusable pack of instructions you can call by name, like a recipe card for a job you do often.

Jev

A model that picks a decision from a list instead of chatting. Fast and cheap for small repeated choices.
